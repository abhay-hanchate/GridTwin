### F-0. The live app trained on an incomplete file (done in the working tree)

  three files into git (about 4 MB); `routes_core.readiness_checks` requires them; the Dockerfile comment is updated;
  `tests/test_scenario_inputs.py` is new.
- **Still to do.** (a) Commit the three parquet files (`git add -f` is not needed after the `.gitignore` change).

### F1. Street animation draws the wrong wires for the switching fix

- **Symptom.** On Fixes, click "Re-route a feeder through a tie switch" (id `switching`) or
  `switching_tap1_volt_var`, then watch the "with fix" view: power flows are drawn on the wrong wires.
- **Root cause.** `backend/v2/compute.py::street_payload` (line 422) sends one `layout` built from the **original**
  street (`engine/street.py::layout(net)`), but `_street_run` (line 399) computes the "after" flows from the
  **candidate's** network (`candidate.network`). A switching candidate removes one wire and adds another, and the
  network's line arrays are re-indexed. For `benchmark_250` with the tie `[26, 31]`:
  wire `(91, 26)` is removed, `(26, 31)` is added, **68 of 95 wire slots change endpoints** (slots 27 to 94), and 30 of
  96 nodes sit in a different place in the switched topology. The frontend
  (`frontend/src/components/street/StreetPlayer.tsx` lines 58 to 72) indexes `run.line_phase_kw[step][ln.line]` with
  the original layout's wire numbers, so flows land on the wrong wires. Home voltages are unaffected (indexed by home).
  The count of wires (95) is the same before and after, which hides the problem.
- **Reproduce** (about 20 seconds):

  ```python
  from backend.v2 import compute
  from engine.fixes.catalog import build
  net = compute.network("benchmark_250")
  scn = compute.robust_set(compute.scenarios("2025-05-15", net, n=60))
  c = next(c for c in build(net, scn, compute.rule("pm10")) if c.id == "switching")
  pa = {(int(a), int(b)) for a, b in zip(c.network.line_from, c.network.line_to)}
  pb = {(int(a), int(b)) for a, b in zip(net.line_from, net.line_to)}
  print(sorted(pb - pa), sorted(pa - pb))      # [(91, 26)] [(26, 31)]
  ```

- **Acceptance.** For a switching fix, every wire of the switched network gets the flows computed for it; the opened
  wire is drawn open (no flow) and the tie wire is drawn and visibly marked; the sum of the three phase powers on the
  root wires equals the "before" sum within the losses; toggling before/after does not make the whole street jump.
- **Suggested approach (B, recommended).** Keep the original layout and key the flows by the **unordered pair of end
  nodes** instead of the wire index. Return, per run, `lines: [{from, to, phase_kw[96][3], neutral_a[96], loading[96]}]`
  (or keep arrays but add a parallel `line_ends: [[a,b],...]` for that run's network). In `StreetMap`, draw wires from
  the original layout; for a pair absent from the layout (the tie) draw a dashed straight connector between the two
  node positions; for a layout wire absent from the run (the opened one) draw it grey and still. Flow sign: the sign is
  "towards the homes" from `engine.street.tree(network)` of that run; when the switched tree orients a wire the
  opposite way to the layout, flip the sign.
  **Alternative (A, simpler).** Return `before.layout` and `after.layout` separately and let `StreetPlayer` use
  `run.layout`; accept that nodes move when toggling.
- **Tests to add.** `tests/test_street.py`: for the switching candidate, assert each run's wire set equals its network's
  wire set and that flow arrays align with the run's own endpoint list. `frontend/src/pages/Overview.test.tsx` or a new
  `StreetPlayer.test.tsx`: render a payload whose after-run has a tie wire and check a dashed tie element and an open
  wire exist.
- **Also check.** Battery candidates: `solve_with_battery` adds a node internally, but `candidate.network` stays the
  base, so layout is consistent; the battery's power is simply absent from the flows (F8).

### F2. The dashboard draws raw probabilities, but gate G8 passes on the calibrated ones

- **Symptom.** The Proof page and `results.json` say the risk chances were recalibrated (isotonic regression) and pass
  gate G8 (calibrated Brier skill +0.51 for ±10% and +0.45 for UP ±6% on held-out 2021 days, both districts). The
  Tomorrow page, the headline, the overview chart and the level (OK/WATCH/ACT) all use the **raw** probabilities.
- **Where.** `backend/v2/compute.py::calibration` (line 200) returns `{"reliable", "raw", "calibrated", "method",
  "held_out_skill"}` from `data/results/risk_calibration_<rule>.json` (`map.x`, `map.y`, applied with `np.interp`).
  `risk_payload` (line 176) returns `p_unsafe` (raw, from `engine.risk.assess_risk`), `level`, `first_watch`,
  `first_act` all raw. The frontend uses only `calibration.reliable`
  (`frontend/src/pages/Forecast.tsx:47`); the chart is `RiskStrip p={risk.p_unsafe}` (`Forecast.tsx:68`), the headline
  `components/Verdict.tsx:16`, the overview hero `pages/Overview.tsx` (via `causeSplit(risk)` in `src/risk.ts`).
- **Decision to make first (write it in `docs/DECISIONS.md`).** Which series do users see, and which series do the
  watch (20%) and act (50%) thresholds apply to? Options: (1) show calibrated when `reliable`, raw otherwise, and
  derive level, first-watch and first-act from the shown series; (2) keep raw as the main chart and add the calibrated
  one as a second line with an explanation; (3) leave raw and delete the claim. Option 1 matches the Proof page; it is
  the recommended one.
- **Implementation notes.**
  - The map was fitted on `fix none`, on the benchmark street, under the named rule. Applying it to a risk replay
    **with a fix** (`/risk?fix=`) or to another street is an extrapolation; show the calibrated series only when
    `fix == "none"` and `network == "benchmark_250"`, and say so.
  - `p_unsafe_without_solar` is raw. `causeSplit` (in `src/risk.ts`) splits raw bars into a grid part and a solar
    part. If bars become calibrated, scale both parts by the same factor per step (`calibrated / raw`) so the split
    keeps its meaning.
  - Level and `first_act` are computed in `engine/risk.py`; either recompute them in `compute.risk_payload` from the
    calibrated series or recompute in the frontend. Keep one place.
  - `home.calibrated` and `home.uncalibrated` strings (en and hi) must change with the decision.
- **Acceptance.** For a rule where `reliable` is true, the chart, the headline times, the level and the "expected
  unsafe hours" agree with each other and with the calibrated series; for a rule where it is false, the raw series is
  shown with the warning; a test in `Forecast.test.tsx` for both cases; `docs/DECISIONS.md` records the choice.

### F8. Wire flows in the street picture are estimates

- **What it is.** `engine/street.py::home_net_kw` and `line_flows` estimate each wire's per-phase power from the net
  power of the homes beyond it. They leave out wire and transformer losses (the gap to the solver was 2.2 to 2.6 kW on
  average, equal to the reported losses), the battery's charge and discharge (`engine/fixes/battery.py`), Volt/Watt's
  extra reduction (code comment in `home_net_kw`), reactive power and the inverters' VAR. The page states "estimated";
  the exclusions are only in the code comment. Neutral current per wire is `|sum of phase currents at 120 degrees|`
  from those estimates.
- **Options.** (1) Cheapest: list the exclusions in `player.flow_note` (en and hi) and in the Proof page.
  (2) Proper: return the solver's own per-wire results. `power-grid-model` can output per-line `p_from`, `q_from`,
  `i_from` for the asymmetric calculation; `engine/solver.py` currently keeps only `line_loading_pct`
  (`DayResult.line_loading_pct`). Extend `DayResult` and the backend (`engine/solver.py` around the `backend.calculate`
  call, `engine/types.py::DayResult`) with per-wire per-phase currents, and replace `line_flows`. This changes
  cached results (rule 1 above) and enables W3 (loading and neutral per wire, exactly).
- **Acceptance (for option 2).** On the benchmark street the sum of root-wire power per step equals the solver's
  `trafo_p_kw` within numerical tolerance, with no loss gap.

## 4. Limitations that stay true after these fixes

These are not defects; they are what the product can and cannot claim. Keep them visible in the README and on the Proof
page.

1. **No real-life check.** No public live household meter data exists, so tomorrow's forecasts cannot be scored day by
   day. The drift monitor checks solar against ERA5 reanalysis, not against rooftop meters.
2. **The street is a benchmark** (SimBench topology with Indian conductors from IS 398), not a surveyed feeder, and
   which phase each home is on is assumed (round-robin). A utility's data replaces both (W7).
3. **For a past day, demand and grid voltage are climatologies.** Demand is the month's typical weekday or weekend curve
   and grid voltage follows the season and the same date of an earlier year, so days of one month look alike at night.
   Only the sunshine is specific to the day. The real tomorrow uses day-ahead models for that date. The replay always
   plays the highest-sun scenario, which is a bad case, not a typical one; random draws use a fixed seed so dates are
   comparable.
4. **The demand model fails its own gate** (G4: skill 9.0% against 10% needed; coverage 78.8% is inside the band). No
   AI-improvement claim is made for demand. It is not used for the scenarios (they use analog days).
5. **G8 passes on the pooled two-district test, not everywhere.** Mathura alone under ±6% is below the base rate
   (skill -3.9, because 99.7% of its January and February steps are unsafe); Bareilly (60 days, January to October) is
   +0.36. The pooled reference is a single rate for both districts, so part of the pooled skill is telling the districts
   apart.
6. **Short test windows.** The Mathura 2021 file ends on 20 February 2021, so time hold-outs cover winter days only
   (51 days for demand, 50 for the upstream-voltage model).
7. **Gate G7 is not run:** the measured-plant yield data (Karnataka, 72 kWp) needs an IEEE DataPort login. Solar yield
   keeps the 14% system-loss assumption.
8. **Weather licence (G6).** Open-Meteo's free API is non-commercial only. A utility deployment needs a paid or other
   licensed weather source.
9. **The grid-voltage input is a proxy.** CEEW measures at homes; the project uses the median home voltage as the
   voltage arriving at the transformer. The model's drop along the wires is added on top, so the transformer voltage may
   be slightly overstated. Not quantified.
10. **Wire flows are estimates** until F8 option 2 (see F8).
11. **Fix costs are physical, not money.** The tournament ranks by solar lost, operations and margin; there are no rupee
    prices.
12. **Deliberately not built** (plan section 3): a neural-network power-flow surrogate, OpenDER, reinforcement-learning
    control, LLM-driven control, SCADA streaming, transactive markets.
